# 2026-11-17 HMR 更新门禁

#39 / 上游 #12510 漏掉的正是这条路径：应用运行中通过 plugin manager 升级，
旧 bundle 先移除、新 layer 再挂载。本记录是 `0.26.3-rc.0` 发布前的门禁运行。

## 环境

- 临时 `DSH_HOME`：`C:\Users\andyz\AppData\Local\Temp\dsh-hmr-gate4`，
  用 `--from-default-profile web` 创建 `gate` profile。web 模板本身包含
  `hmr` 与 `plugin-manager` 行（`--dump-config` 确认）。
- 先用 registry 安装 `dsh-plugin-wsl-env@0.26.1`（`dsh plugin --profile gate add`），
  `dsh.profile.bundles` 含该 bundle。
- 候选版本：`0.26.3-rc.0`（npm `next` tag）。
- 一个活动会话：`createSession({cwd: <临时 Windows 工作区>})`，preset 为
  `standard`，在升级期间保持存活。

## 方法

临时 profile 上叠加一个探针行（不放进插件 bundle），探针在独立任务里：

1. 创建活动会话；
2. 调用真实的 `pluginManager.updateBundle("dsh-plugin-wsl-env", "0.26.3-rc.0")`；
3. 记录 `from/to/step`、`result.application`、`changed`、`restore`、
   三个服务的当前实现类；
4. 退出 host。第二次启动用 `verify` 模式只读三个服务的实现类。

探针的 `apply` 必须立即返回，更新放在 unattached 的异步任务里。否则探针自己的
fiber 会在 profile 重组时被 loader 等待，形成探针与更新的死锁；这几轮调试中出现
过该现象（update 在 `step=remove` 挂起 180 秒）。

## 结果

对 registry 安装路径（用户实际升级路径）：

```
update from=0.26.1 to=0.26.3-rc.0 step=install
result application=applied changed=true stage=enable error=null
restore=null
providers-now={"subprocess":"WslSubprocessRuntime","fs":"WslRoutingFileSystem","directoryPicker":"WslDirectoryPicker"}
UPDATE OK
```

升级后 profile 的 `dsh.profile.bundles` 仍含 `dsh-plugin-wsl-env`，安装版本
`0.26.3-rc.0`。重启后验证：

```
providers={"subprocess":"WslSubprocessRuntime","fs":"WslRoutingFileSystem","directoryPicker":"WslDirectoryPicker"}
VERIFY OK
```

## 边界与另一个发现

- 本门禁用 headless web composition（loader / plugin-manager / hmr 行与桌面版
  相同），没有用桌面 GUI 点击升级；GUI 只多一层客户端调用。
- 同一套探针换成 **Git 固定 commit** 依赖时，更新报告
  `application: applied`，但重启后 `dsh.profile.bundles` 丢失了
  `dsh-plugin-wsl-env`，三个服务回到 shipped。这是 Git 安装路径的独立问题，
  不影响 registry 升级路径；需要单独立项排查（plugin manager 的
  remove/install/enable 写入时序）。2026-11-19 在 0.2.2-rc.5 上用同一对 commit
  复验不再复现，详见 [2026-11-19-hmr-gate-rc5.md](2026-11-19-hmr-gate-rc5.md)。
- 一次在探针 `apply` 中直接 await 更新的运行在 `step=remove` 超时，被终止后
  留下 `package.json.lock`；这是探针死锁的副产物，不是 registry 路径的结论。
